# 中交 Demo

面向中交三项测试业务：立项材料审查、立项书起草、Excel按单位拆分。

当前仓库已建立文档及协作目录，业务代码、依赖版本和部署配置尚未实现，因此目前没有可运行的服务。

## 技术栈

| 层次 | 工具 |
| --- | --- |
| 后端 | Java＋Spring |
| 前端 | Next.js＋React |
| 数据库 | MongoDB |
| 接口定义与测试 | Apifox |
| 代码版本与环境配置 | Git |
| 容器化部署 | Docker |

具体运行时和依赖版本在工程初始化时统一锁定。前端通过Java接口访问业务能力，WorkBuddy通过适配层复用同一后端。

## 两人协作

1. A主责后端、模型与审查；B主责前端和Apifox联调，并按分工协助业务模块。
2. 开始开发前，双方先确认接口字段、状态、错误格式和任务文件约定。
3. 各自在功能分支开发，例如 `feature/review-backend`、`feature/task-ui`。
4. 提交说明写清改动、影响接口、验证结果和未完成事项；检查后合并到 `main`。
5. 联调检出同一提交；可演示版本使用Git标签标识。首次演示验收通过后再创建发布标签。
6. 两人给各自GPT提供同一版本的需求、技术栈和接口说明；实际成果通过Git交接。

Git同步代码和环境定义，Docker按配置构建运行环境。容器、数据库和本地软件不会随Git自动同步。

## 文件与配置

- 提交前后端依赖声明、依赖锁文件、构建工具版本、Docker配置、Apifox导出和配置样例。
- 真实密钥与本地 `.env` 不入库；可以提交脱敏的 `.env.example`。
- 原始客户素材、数据库文件和生成的报告不入库，按指定渠道单独交接；使用校验值确认素材版本。
- Word和Excel按扩展名默认忽略；受控模板按具体内容确认后放入 `templates/`（该目录豁免忽略），以便管理必要模板。

## 首个开发里程碑

先打通真实拆表流程：上传 → 创建任务 → 拆分并全量核对 → 查询状态 → 下载。

之后按同一任务与文件接口接入审查、起草和WorkBuddy。审查及起草的模型运行接口仍需实际确认。最终检查原表审查要求覆盖、7组需求及模板结构、50个单位文件和明细一致性。
